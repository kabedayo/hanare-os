# HANARE v0.1 設計メモ

作成: 2026-11-02 / 状態: 初稿（GitHub初公開に向けた最小設計）
前提: README の「人間側 / AI側 分割」コンセプトを、既存の実機で動く形に落とすこと。

---

## 1. v0.1 のゴール / 非ゴール

### ゴール
1. Ubuntu 24.04 の1台を「人間側（GTX 1060）／AI側（V100）」に**再現可能な手順**で分割できる。
2. AI側サービス（llama-server、ComfyUI）が端末の手起動ではなく、状態を確認できる管理単位として上がる。
3. 人間側から AI側の状態（GPU・VRAM・サービス死活）を**読み取り専用**で見られる。
4. VRAM の取り合いについて、暗黙の奪い合いではなく**明文化したポリシー**がある。

### 非ゴール（v0.1 ではやらない）
- Linux カーネルの改造・フォーク、カスタムディストリの ISO 化
- QEMU/KVM による V100 パススルー（v0.3 候補。IOMMU グループ確認から別途）
- VRAM スケジューラの自動調停（v0.2 候補。v0.1 はポリシーの明文化まで）
- 単一GPU機への完全対応（劣化モードの検討のみ）
- ゲーム性能の最適化（人間側は「壊さない」ことが目標）

## 2. 実機前提（最初のテストベッド）

| 項目 | 実測値（2026-11-01〜02 確認） |
|---|---|
| OS | Ubuntu 24.04.5 LTS / GNOME 46 |
| CPU / RAM | Ryzen 7 5700X / 48GB（16GB×3、空き1スロット） |
| 人間側GPU | GTX 1060 6GB（index 1、画面出力担当想定） |
| AI側GPU | Tesla V100-PCIE-32GB（index 0、sm_70、表示出力なし） |
| ドライバ | NVIDIA 580.178.04（CUDA API 13.0 表示） |
| ディスク注意 | ルートは使用率約90%・空き約96GB。モデル/データは大容量データディスク（/mnt/HDD、空き約788GB）へ置く |

### 既知の地雷（v0.1 で最初から回避する）
- **llama.cpp は V100 で CUDA ビルドがクラッシュした実績あり**（ggml_cuda の PDL まわりで abort）。動作実績があるのは **Vulkan ビルド（build-vulkan）**。v0.1 はこちらを正規ルートとして固定し、理由をコメントに残す。
- PyTorch は **cu126 + sm_70 を含むビルド必須**（例: torch 2.7.1〜2.14.1+cu126 系で動作確認済み）。cu132 系は sm_70 カーネルが無く動かない。
- CUDA ツールキット（nvcc）・conda は実機に無い。新規 Python 環境は uv のマネージド Python 等、コンパイル前提にしない方法を選ぶ。
- **共有サーバーの停止は他作業を壊す。** ComfyUI のキューが空でも、別タスクが起動・準備中とは限らない。v0.1 の管理単位は「止める前に依存/利用中タスクを表示する」を必須要件とする。

## 3. 構成

```text
repo (想定)
├─ README.md
├─ docs/
│  └─ design-v0.1.md        ← 本書
├─ setup/
│  ├─ 00-check.sh           ハードウェア/OS/ドライバの事前確認（読み取りのみ）
│  ├─ 10-pin-gpu.sh         AIサービスのGPU固定（環境変数/ユニットへの反映）
│  └─ 20-services.sh        AI側サービスのユニット配置
├─ services/
│  ├─ llama-server.service  (systemd unit、system/user の別は §6 の未決事項)
│  ├─ comfyui.service
│  └─ ai-os.env             GPU index・ポート・モデル置き場の集約
├─ status/
│  └─ status.sh             nvidia-smi + サービス死活を JSON で出す（人間側/ AI 両対応）
└─ policy/
   └─ vram-policy.md        VRAM 配分と競合時の振る舞い
```

### GPU 固定の方針
- AI側サービスは `CUDA_VISIBLE_DEVICES=<V100のindex>` を必ず付ける。index は機種名（Tesla V100）で解決し、数字のハードコードだけに頼らない（枚数や順序が変わる機体への配慮）。
- 人間側デスクトップ / ゲームには AI側の VRAM を一切使わせない。逆も同じ。
- 確認コマンド: サービス起動後に `nvidia-smi` でプロセスが V100 側にだけ居ることをチェックし、結果をログに残す。

### サービス定義（v0.1 の対象は2つだけ）
| サービス | ポート | API | 備考 |
|---|---|---|---|
| llama-server | 127.0.0.1:8080 | OpenAI互換 | Vulkan ビルド固定。モデルはデータディスクから読む |
| ComfyUI | 127.0.0.1:8188 | HTTP API | 出力先はデータディスク配下に固定 |

- 既存の上位アプリ（例: Local Story Studio / 127.0.0.1:8765）は v0.1 の管理対象に**入れない**。v0.1 は土台の2サービスまで。アプリは「AI側の利用者」として扱う。
- 公開範囲は当面 localhost のみ。LAN/外部公開は認証設計とセットで v0.2 以降。

### 状態表示・開閉管理・リソース監視（status）★ v0.1 の中核機能

背景（2026-11-02 ユーザー要件）: AI が裏で起動する時代になると「今そのAI/サービスが
開いているのか閉じているのか」すら分からないことが多い。実例も今日あった:
画面フリーズ時の確認で、成果物は完成済みなのに CPU 0% の Blender プロセスだけが
約80分残っていた（＝動いているように見えて実は終わっている残骸）。
対策を「なんとなく ps で見る」ではなく、OS の機能として持つ。

#### (a) 開閉状態の管理（誰が・いつ・何のために開いたか）
- AI側サービスは全て**レジストリ**に登録する: 名前、起動コマンド、ポート、担当GPU、
  ログの場所。登録外のプロセスは status で「未登録」として見えるようにする。
- systemd unit 経由の起動・停止のみを正規の開閉とする（端末から直接起動したものは
  「管理外」として区別表示する。禁止はしないが、見分けがつくことが対策になる）。
- 起動・停止・異常終了のイベントを JSONL ログに追記する: 時刻、サービス名、
  イベント種別、起動者（どのタスク/チャットか分かる範囲で）、PID。
- 状態モデルは4値に固定する:
  `running`（プロセスあり＋ポート応答あり）/
  `stopped`（プロセスなし）/
  `degraded`（プロセスはあるがポート応答なし、またはその逆）/
  `stuck-suspect`（プロセスはあるが後述の停滞条件に該当）。

#### (b) 停滞検知（終わっているのに残っているプロセス対策）
- 目安条件: 一定時間（初期値10分）CPU使用率がほぼ0%のまま、
  かつログ/出力ファイルの更新も無いプロセスを `stuck-suspect` と表示する。
- v0.1 では**自動で殺さない**。旗を立てて人間に見せるところまで（誤判定で作業を壊す方が悪い）。
  自動終了の可否は v0.2 で、対象サービスの性質ごとに決める。

#### (c) リソース監視（VRAM / RAM）
JSON と人間向け表示の両方で、少なくとも次を出す:
- GPU ごと: 名前、VRAM 使用/総量/空き、利用率
- プロセスごと: PID、名前、VRAM使用量（`nvidia-smi` の compute-apps 相当）、
  RAM使用量（RSS）、CPU%、起動時刻、経過時間、状態（上記4値）
- システム全体: RAM 使用/総量/空き、スワップ使用量
- サービスごと: 起動状態、ポート応答、（可能なら）現在のジョブ/キュー有無
- 最終チェック時刻

取得は読み取り専用コマンド（`nvidia-smi`、`free`、`ps`、`ss`）のみで行い、監視自体が
対象を止めたり再起動したりしない。

#### (d) 表示
- 正は CLI: `status` が人間向けテーブルと `--json` の両方を出す。
- 人間側ダッシュボード（status JSON を表示するだけの薄い読み取り専用ページ）は
  **v0.1 に含める**（2026-11-02 決定。当初は後半の任意項目だったが、監視が要件に
  なったため格上げ）。更新間隔は初期値5秒、操作ボタンは置かない（見るだけ）。

#### (e) ライブ活動フィード（「今、何が動いているか」の実況）— 2026-11-02 追加要件

(a)〜(d) が「状態」の監視なら、こちらは「活動」の監視。動機（ユーザーとの対話から）:
llama.cpp の Web UI (8080) に流れるのは自分のチャットだけで、API 経由の推論や
エージェントの作業は表に出てこない。「Qwen が働いているところを見たい」が
今の道具立てでは満たせない。これを監視システムの要素として取り込む。

取り込む活動は3種類:
1. **推論活動**: llama-server のタイミングログ（task開始/完了、生成トークン数、
   tokens/sec、プロンプト処理速度）をイベント化する。どのモデル宛かも含める。
   ※ サーバーの標準出力が起動ターミナルに流れる現状のままでは収集できないため、
   HANARE 管理下のサービスは**標準出力を必ずファイルに残す**ことを要件にする
   （systemd の `StandardOutput=append:` 等。v0.1 の unit 設計に含める）。
2. **エージェント作業活動**: muse-bridge / OpenCode 等のタスク実行は、開始時に
   タスクID・依頼者・タスク名を、実行中はその出力ログを、共有の活動ログ置き場に
   リアルタイムで流す（`tee` 相当）。人間は `tail -f` でもダッシュボードでも追える。
3. **リソースの動き**: (c) のスナップショットを一定間隔で JSONL に追記し、
   ダッシュボードで VRAM / RAM の直近の推移（初期値: 直近1時間）を折れ線で見られる
   ようにする。保存は間引いてよい（例: 5秒間隔×1時間＋1分間隔×24時間）。

イベントの共通形式（JSONL 1行1イベント）:
`{ts, kind: inference|agent|service|resource, actor, name, detail, ...}`
actor（誰の依頼か）が分かる範囲で必ず付ける。「誰が何をやっているか分からない」への対策が目的なので、actor 空欄のイベントは設計として負けとする。

ダッシュボードへの統合: (d) のページに活動フィード欄（新しい順のイベント列）を足す。
操作は引き続き無し（見るだけ）。フィードの配信は status JSON と同じく読み取り専用経路のみ。

## 4. VRAM ポリシー（v0.1 は明文化まで）

実機の同時占有例（2026-11-01 実測）: llama-server 約8.6GB + ComfyUI 約7.2GB ≒ 16GB / 32GB。

v0.1 のルール案:
1. **常駐枠**: llama-server と ComfyUI の同時常駐を標準とし、合計の目安上限を 24GB とする（残りは生成時の一時膨張用）。
2. **大きなモデルを載せ替える時は明示操作**にする。自動で他サービスを落とさない。
3. **停止操作は影響表示付き**: 対象サービスを利用中の可能性がある作業を警告してから止める。
4. 自動調停（キューを見て載せ替える等）は v0.2 のスケジューラで扱う。本書ではルールのみ定義する。

## 5. 検証手順（v0.1 リリース条件）

1. `00-check.sh` が対象外環境（単一GPU、ドライバ不足 等）を検出して止まること。
2. セットアップ後に再起動し、手操作なしで2サービスが上がること。
3. ゲーム等の人間側アプリを起動した状態でも、AI側サービスが GTX 1060 の VRAM を使っていないこと（`nvidia-smi` で確認）。
4. AI側で LLM 推論と画像生成を同時に叩いても、§4 の上限内で収まる／超える場合は明確なエラーになること（無言の OOM や相手のプロセス道連れにしない）。
5. `status` の JSON が、人間側・AI側どちらからでも取得できること。
6. 既知のプロセスを意図的に「応答なしポート＋プロセスあり」にしたとき `degraded` と表示されること。また、CPU 0% で放置したダミープロセスが閾値経過後に `stuck-suspect` と表示され、自動では終了されないこと。
